{# ========================= Pipeline ========================= #}

How a flow becomes a verdict

The same five steps run whether the flow is typed in by hand, read from a CSV, or captured live off an interface.

  1. 1

    Capture

    Packets are grouped into bidirectional flows keyed on the 5-tuple, and closed on FIN or timeout.

  2. 2

    Extract

    Each flow is reduced to {{ feature_count }} numbers: duration, rates, inter-arrival gaps, header and flag counts.

  3. 3

    Align

    Column names are mapped to the training schema, infinities and gaps repaired, order fixed.

  4. 4

    Classify

    A tuned gradient-boosting model scores all {{ class_count }} classes — scaling applied first for the MLP.

  5. 5

    Report

    The top class, its family and the full probability spread, logged to history for later review.

{# ========================= Under the hood ========================= #}

How it was built

Each stage lives in its own notebook, so any number on this page can be traced back to the run that produced it.

Cleaning & feature selection

Duplicate and infinite rows dropped, {{ class_count }} classes consolidated, then the feature set cut from 80 columns to the {{ feature_count }} that actually carry signal.

CTGAN for the rare classes

SQL Injection and the web attacks are a few dozen rows against millions of benign ones. Synthetic samples were generated per class and checked column-by-column against the real distribution.

Optuna tuning

Hyperparameters for each model were searched with Optuna and frozen to JSON, so every later run reuses the exact same configuration.

Data-size scaling study

All models retrained at 25k / 100k / 281k rows with frozen hyperparameters and one fixed test set, isolating the effect of data volume alone.
