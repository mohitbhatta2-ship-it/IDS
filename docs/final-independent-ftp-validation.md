# Final independent FTP validation

**All models frozen (production, Candidate 2, the robust behavioural candidate, and the
three ablation models are byte-for-byte unchanged; ml.py / live_capture.py /
pcap_validation.py unchanged; verified before == after). The independent corpus is
TEST-ONLY — never training, weighting, threshold, feature, or hyperparameter selection.
No promotion, no merge.** Branch `claude/final-independent-ftp-validation`.

## Why this test exists

Every prior corpus — including the messy train/test corpora that produced the robust
candidate's perfect 1.000/1.000 — was generated by the **same family of scenario
functions**, on loopback, with the same two server implementations (pyftpdlib + a
bespoke raw-socket server). The robust-retraining report flagged this explicitly: the
perfect score showed generalisation across new addresses/ports/users for the *same
behaviours*, not to a genuinely different stack. This experiment builds that different
stack and re-tests.

## What makes this corpus genuinely different

| Axis | Every prior corpus | This corpus |
|---|---|---|
| FTP server | pyftpdlib + custom raw-socket | **vsFTPd 3.0.5** (real production daemon, never used before) |
| Client | ftplib / curl / wget / raw-socket | **lftp** (new) + curl / ftplib / raw-socket |
| Network | loopback (`lo`), 127.0.0.0/8 | **non-loopback** veth pair to an isolated `ip netns`, `10.77.0.0/24` |
| Scenario code | `robustness_capture` / `robust_train_capture` | **fresh** `independent_ftp_lab` (written from scratch) |
| Encryption | none | **FTPS/TLS** captured separately |

**28 fresh PCAPs (16 Benign, 12 FTP-BruteForce; 4 FTPS), 162 flows, 0 incomplete**,
hash-disjoint from all six prior corpora. Real vsftpd failure delays give realistic
timing (brute force 15–43 s, not sub-second loopback). Labels come from the scenario
folder, never a prediction.

### What this proves — and what it does not

- **Proves:** whether the robust candidate generalises to a *different server
  implementation, a different client, and a genuine non-loopback network path*.
- **Does NOT prove:** generalisation to a different **OS**, separate physical hosts /
  VMs, the public internet, or FTP dialects beyond vsftpd. This is still one container,
  one server implementation, cleartext + one FTPS config. The `ip netns` gives a
  separate network stack and a real non-loopback interface — not a separate machine.

## The headline finding — split verdict

**Attack detection is robust and shortcut-free. Benign-authentication-failure handling
is not robust on a new stack.**

Per scenario family (robust candidate):

| Family | Label | flows | recall | reading |
|---|---|---|---|---|
| fast_brute / slow_brute / multi_conn / user_enum | FTP | 63 | **1.000** | every brute-force variant caught |
| eventual_success (attacker guesses right) | FTP | 7 | **1.000** | not fooled by the successful 230 |
| clean / activity / multi_user / reconnect | Benign | 44 | **1.000** | normal benign never flagged |
| **mistype** (benign fails then succeeds) | Benign | 12 | **0.667** | 4/12 flagged as attack |
| **gave_up** (benign fails then quits) | Benign | 5 | **0.000** | 5/5 flagged as attack |

The robust candidate catches **100%** of attacks (FTP recall 1.000, precision 0.886)
and beats Candidate 2 enormously (FTP recall 1.000 vs 0.086). But **benign sessions
that fail to authenticate** — `gave_up` (0/5) and some `mistype` (4/12) — are flagged
as attacks, pushing benign recall to 0.852 (< 0.90) and FPR to 0.148 (> 0.10).

**Why:** a benign user who mistypes and then gives up produces traffic that is
essentially *identical at the network + control-channel level* to a small failed
brute-force attempt (several `530`s, no `230`). vsFTPd's real per-failure delays make
these benign-fail sessions span 9–15 s — temporally very much like slow brute force.
The previous corpus's `gave_up` timing (fast loopback) was learned; vsftpd's timing is
different, so the memorised separation does not transfer. This is a genuine
generalisation gap the shared-methodology corpora hid — exactly what an independent
test is for.

## Does the robust model still depend on…?

Measured by SHAP (cleartext) + ablation on this genuinely new traffic:

- **`ftp_failed_logins`** — **No.** SHAP share **3.7%** (rank 5); removing it drops FTP
  recall by **0.000** (still 1.000). Not a failed-login shortcut.
- **successful authentication** — **No.** SHAP share **0.2%**; attacker-eventual-success
  recall **1.000** (the 230 does not flip attackers to benign).
- **CIC artifacts** — **Partly, not dominantly.** Share **42.8%** (`Dst Port`,
  `Fwd Seg Size Min`, `Init Fwd Win Byts` lead), below a 50% majority.
- **any single application-layer feature** — **No.** Largest single behavioural share is
  `ftp_failed_logins` at **3.7%**.

So the model uses broad flow + behavioural context, not a single proxy — its errors are
**not** a shortcut artefact; they are the inherent benign-fail / brute-force ambiguity
surfacing on a new stack.

## FTPS / TLS (encrypted — behavioural features unavailable)

Under TLS the control channel is encrypted, so the 15 behavioural features are
genuinely **0/unavailable** (verified: `ftp_login_attempts = 0` on all FTPS captures).
The behavioural models therefore fall back to their 30 CIC-artifact behaviour and, like
production, do **not** detect FTPS brute force (FTP recall 0.000; benign recall 1.000).
This is expected and is called out, not hidden: **cleartext-FTP behavioural detection
does not extend to FTPS** — encrypted FTP brute force needs a different (e.g.
flow/timing or TLS-metadata) approach.

## Verdict — NOT ROBUST

`final_verdict.json`: `verdict = "NOT ROBUST"`, `promote = false`.

Against the promotion criteria, on genuinely different traffic the robust candidate:

- FTP recall 1.000 ≥ 0.70 ✓, but benign recall 0.852 < 0.90 ✗ and FPR 0.148 > 0.10 ✗;
- beats Candidate 2 (✓), is not a `ftp_failed_logins`/auth/single-feature shortcut (✓);
- benign-that-fails recall 0.47 (✗) — the deciding weakness.

**Honest reading:** this is not a regression to uselessness — the FTP-detection
dimension is excellent and robust, and the model is genuinely not a shortcut. But the
benign false-positive problem that the shared-methodology corpora had hidden is **real
and reproducible on an independent stack**, so the candidate is **not ready for
promotion**. The previous phase's 1.000/1.000 was optimistic, precisely as its caveat
warned.

### What would move this toward promotion
- Training benign-authentication-failure traffic from **multiple real servers** (varied
  failure timing), so the model stops relying on any one server's timing signature.
- An explicit decision about the `gave_up` / failed-brute boundary: these are
  near-indistinguishable at the network level, so a product may need a policy (e.g. a
  rate/volume threshold, or accepting that "many failed logins, no success" is treated
  as suspicious regardless of intent).
- Broader independent tests (different OS, real hosts, more FTP servers, FTPS-aware
  features).

python manage.py final_independent_ftp_validation        # evaluate frozen models, SHAP, ablation, CIs
python manage.py test predictor.tests.IndependentFtpLabFrameworkTests \
                      predictor.tests.IndependentFtpCorpusArtifactTests \
                      predictor.tests.FinalIndependentValidationResultsTests
